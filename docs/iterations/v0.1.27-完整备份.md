# 0.1.27：完整备份与恢复

[返回版本迭代计划](../版本迭代计划.md)

状态：代码与自动化已实现；iPad 文件分享、容量和跨设备播放待验收。前置版本：0.1.26。结果见[验收记录](../验收/0.1.26-0.1.27-验收记录.md)。

## 1. 用户结果与范围

家长导出一个文件，在另一台设备或独立干净实例中导入后，孩子档案、词表、短句、学习进度、相册照片及全部家长录音都能使用。

首版只做完整替换恢复，保留旧 JSON 导入兼容；不做设备间合并、增量同步、云端账号或自动上传。备份包含所有档案，不能误用只含当前孩子内容的界面投影。

## 2. 备份内容与容器

已采用单个 `learning-desk-日期时间.learningdesk.zip` 文件，包含：

| 内容 | 说明 |
| --- | --- |
| `manifest.json` | 备份种类、容器格式版本、App 版本、存储 schema 版本、导出时间、资源数量、文件清单 |
| `state.json` | 原始完整状态，包括所有档案及设置；保留 0.1.26 的关内结果 |
| `assets/` | 相册照片、单词录音、短句录音、书页录音的实际文件 |

文件清单记录内部资源 ID、安全相对路径、大小和完整性校验值。同一实际文件被多处引用时只打包一次，并记录引用关系。打包只遍历状态引用的家庭资源，不扫描设备中无关文件。

新容器使用 `format: 2`；旧 JSON 的 `format: 1` 仍可导入。对未知格式及未支持的存储 schema 拒绝并提示需要更新，不能直接丢弃字段后恢复。

归档采用纯 JavaScript `fflate`，输出无压缩 STORE ZIP；读取仅接受学习台生成的同种容器，拒绝其他压缩方式、加密、分卷和 ZIP64。该选择避免声明解压大小与真实膨胀长度不一致。Node 二进制往返与 iOS 打包已通过，27-01 仍须验证实际 Expo Go/SDK 57 真机流程。

## 3. 文件能力验证与当前参数

已通过 Context7 查询的官方文档支持以下一般设计：

- [DocumentPicker](https://docs.expo.dev/versions/latest/sdk/document-picker/)：通过系统文件选择器选择备份；立即读取时复制到应用缓存。
- [Sharing](https://docs.expo.dev/versions/latest/sdk/sharing/)：在 iOS/Android 分享本地文件；Web 对本地 URI 的能力不同。
- [FileSystem](https://docs.expo.dev/versions/latest/sdk/filesystem/)：读取和写入备份文件。

已通过 Expo 兼容安装加入 `expo-document-picker ~57.0.3`、`expo-sharing ~57.0.22` 与 `fflate ^0.8.3`，沿用 `expo-file-system ~57.0.7`。锁文件固定具体解析版本，尚未验证 iPad 系统文件流程。

当前保护值：最多 500 个媒体文件 / 1000 处引用，单文件 8 MiB，总内容 48 MiB，ZIP 最大 50 MiB，额外空间余量 16 MiB。恢复时重复引用各自写独立文件，展开后总媒体仍受 48 MiB 限制；避免删除某一条录音后破坏另一条引用。这些是保守工程限制，须经下述真机容量验证后调整。

自动化已验证 30 张各 256 KiB 的模拟照片与 60 段各 64 KiB 的模拟录音往返；这证明二进制一致性，不证明图片解码、音频播放或设备内存表现。

27-01 需要产出以下记录，而不是只确认“能安装”：

1. 候选归档方案能否在 Expo Go 中读写二进制资源，取消/失败后能否清理临时文件。
2. 小包：1 张照片、单词/短句/书页各 1 段录音；验证导出、选择、读回和播放。
3. 常用包：30 张测试照片、60 段短录音；记录文件大小、耗时、可观察的内存与剩余空间要求。
4. 容量边界：用人工测试资源逐步增加大小，确定最大文件数、单文件大小、解压后总大小和空间余量。
5. 将验证出的限制写进本规格与应用提示。超过上限时在替换数据之前停止，不假装成功。

若归档方案不可用，先记录具体阻塞并重新确定容器；不把“文本备份成功”当作本版完成，不因文件选择器能返回 URI 就宣称恢复成功。

## 4. 导出流程

1. 在家长书桌点击“导出完整备份”。
2. 固定本次完整状态快照，统计档案、词、短句、照片和录音数量。
3. 检查引用媒体是否可读取；临时 URI 仍可读取时将文件纳入包，失效时列出具体缺失项。
4. 复制引用媒体并打包，计算清单校验值。导出期间禁止会改变该快照资源的编辑/删除操作。
5. 写入成功后打开系统分享面板，家长自行选择保存位置。

“已生成备份文件”和“已保存到外部位置”分开描述。系统面板的返回不一定能证明用户已经保存，取消分享不能显示“已保存”。

缺失媒体时默认停止完整备份并列出书名/页码或词条；允许用户另选原有“仅数据 JSON 导出”，但必须标记不含完整媒体，不能作为本版完整恢复验收样本。

## 5. 导入与失败保护

导入状态顺序：选文件 → 校验 → 内容预览 → 家长确认替换 → 暂存媒体 → 提交新状态 → 验证可读 → 完成。

- 选择文件、取消选择和查看预览不会改变现有数据。
- 预览展示来源版本、导出时间、档案/词/照片/录音数量和当前将被替换的数量。
- 确认文案明确所有本机档案都会替换。先创建可恢复的当前状态与媒体快照，再开始提交。
- 对 JSON 语法、schema、资源完整性、路径、引用关系、数量/大小上限做校验。
- 拒绝绝对路径、`..` 路径越界和重复冲突条目；按解压后大小限制包，不能只看压缩文件大小。
- 媒体先写入新的受管理位置，不覆盖当前状态引用的旧文件；成功后重建照片和录音引用。
- 新路径仍须被现有媒体解析、受管理路径判断及删除逻辑正确识别，避免恢复后能看却无法清理。
- 全部资源就绪后再持久化新状态；失败或空间不足时旧状态和旧媒体可继续使用。
- 状态提交前后要能识别未完成恢复。冷启动时继续验证或回退，不能停在一半新数据、一半旧数据。
- 完成恢复并验证新状态可读后才清理旧媒体/暂存文件；失败时不得删除原资源。清理必须限于本次管理的路径。

同步收紧 `loadState` 的失败路径：原始存档读取/解析/迁移失败时，保留原数据，展示恢复或重试入口；不要自动播种示例并被自动保存覆盖。首次无存档与存档损坏必须能区分。

旧 JSON 在同一设备上可保留仍有效的媒体引用；换设备时预览明确说明媒体不在文件里，并报告不可用引用。导入旧 JSON 不应被标记为完整媒体恢复。
